# SayMake

> 用人话说一句，拿到一个能直接玩的东西。
>
> Say it plainly. Get something that works.

SayMake 是一个开源的 AI Skill：不会写代码、不懂提示词工程的人，用一句自然语言描述想要的小游戏，它负责把这句话变成**明确的需求规格**、**能跑的单文件 HTML 游戏**、**自动验收**，并且支持"指哪改哪"的局部修改。

它不是一个提示词合集。仓库里真正干活的是脚本：验收器和补丁器。

## 它解决什么问题

现在的 AI 工具很强，但想让它们做出"你心里的那个东西"，你得会写精确的提示词、懂模型、懂行业惯例、看得懂术语。这些门槛对普通人来说太高了。

SayMake 的做法是把提示词工程从用户侧搬到系统侧：

- 用户只负责**说人话**
- 系统负责**补全规格**（把没说出口的假设显式化，让用户确认）
- 系统负责**填行业惯例**（八成决策不该问用户，直接给默认值）
- 系统负责**验收**（能跑、不报错、手机上不乱，这些由脚本检查，不由模型口头保证）
- 系统负责**精确修改**（"这块大一点"只改那一块）

## 五分钟试用

```bash
git clone https://github.com/pengyicai203-gif/saymake
cd saymake

# 1. （可选，推荐）装真实浏览器验收环境，装到 ~/.saymake/，不碰仓库
bash skills/make-game/scripts/setup_browser.sh

# 2. 跑验收器
node skills/make-game/scripts/validate_game.mjs examples/fruit-catch/index.html --browser
```

你会看到一份通过/不通过清单，以及 `examples/fruit-catch/.saymake/` 下两张截图：开始页和运行中的画面。把 `examples/fruit-catch/index.html` 在浏览器里打开，就是一个能玩的接水果小游戏——它和 `examples/tap-the-dot/` 一样，也是验收器的测试样本。

## 装到你的 AI 工具里

把 `skills/make-game` 整个目录复制到你 AI 工具的 skills 目录（不同工具位置不同，常见的是用户目录或工作区下的 `.skills/`）。**装完重开一个对话**，skill 列表是在会话启动时加载的。然后对它说：

> 我想做一个接水果的小游戏，手机上玩。

它会先复述一遍它理解的需求（最多追问两轮），然后生成游戏、自动验收、给你看截图、告诉你在哪、还能怎么改。

## 它怎么工作

四个部件，判断交给模型，确定性交给脚本。

| 部件 | 位置 | 形态 | 职责 |
|---|---|---|---|
| 协议 | `skills/make-game/SKILL.md` | 指令 | 查经验 → 判断五个问题（审美、玩法、机制、字体、受众）→ 拿不准就用带画面的选项问 → 做 → 看图自检并留痕 → 交付 → 记下这一轮学到的 |
| 惯例库 | `skills/make-game/data/*.json` | 数据（社区维护） | **选项库 + 判断指南**，每条带出处：16 种视觉方向、11 个玩法（怎么做、默认数值、难度旋钮）、21 种机制 + 3 条反模式、5 种字体方向、4 种受众（给谁玩，具体改什么）、信号→方向的映射、问题库、提问预算、"太丑/不好玩"的诊断清单、5 条出厂判断案例 |
| 经验库 | `skills/make-game/scripts/log.mjs` + `~/.saymake/memory/` | 脚本 + 本机数据 | 跨项目记住这个用户：偏好、做过的项目、踩过的坑、判断案例。开工时按相似度带出来，做完写回去。纯文本，一条命令看和删 |
| 按需读库 | `skills/make-game/scripts/library.mjs` | 脚本 | 先读 1500 字的清单，选中哪条再读哪条。之前每次要读约 5 万字 |
| 验收器 | `skills/make-game/scripts/validate_game.mjs` | 脚本 | 单文件、语法、契约标记、禁止弹窗；`--browser` 模式下真实打开页面检查报错、溢出、开始/计分/重开，并留两张截图 |
| 库校验器 | `skills/make-game/scripts/check_library.mjs` | 脚本 | id 唯一、字段齐全、跨库引用有效、出处格式正确——库靠社区长，不能长坏 |
| 浏览器环境 | `skills/make-game/scripts/setup_browser.sh` | 脚本 | 一键把 playwright + Chromium 装到 `~/.saymake/`，不污染 skill 目录 |
| 补丁器 | `skills/make-game/scripts/patch_css.mjs` | 脚本 | 把"这块大一点"写成可追溯、可清除的样式覆盖，不碰其余部分 |

生成器和验收器之间有一份**契约**（见 `conventions.json` 的 `contract` 字段）：游戏必须带 `data-sm="start|score|restart"` 标记，并暴露 `window.__sm.start()/getScore()/restart()/isRunning()`。有了契约，验收才是确定性的，修改才能落到具体位置。

## 它会记住你

这是 SayMake 和"一段提示词"最不一样的地方。用得越久，它越知道你是谁：

- **偏好**："想要更真实的画面，背景简单一点""直接做，少问"
- **踩过的坑**：问题是什么、原因是什么、怎么解决的——下次直接绕开
- **判断案例**：你说过什么、它选了什么方向、对没对上、教训是什么

这些存在你自己电脑上的 `~/.saymake/memory/`，是纯文本，不上传，不随 skill 升级丢失，同一台电脑上的不同 AI 工具读同一份。每次开工，它先把和这句话相关的部分拿出来看；做完，把新学到的写回去。

```bash
node skills/make-game/scripts/log.mjs show          # 看它记了你什么
node skills/make-game/scripts/log.mjs forget <id>   # 说"这条不对"就删掉
```

## 核心原则

1. **判断交给模型，确定性交给脚本。** 模型负责理解、判断、提问、生成；验收一律跑脚本，然后看截图。绝不相信"我做完了、能跑"。
2. **脚本验"能不能用"，截图验"对不对"。** 前者可执行可回归；后者由模型对照所选方向自检。
3. **惯例是选项库，不是规则。** 十六种视觉方向、二十一种机制、五种字体方向，每种都写了适合和不适合。用户要复古，emoji 就是对的。库不够用就合成一个方向，用户认可后加回库里。
4. **判断不准就问，问的是画面不是技术。** "像现在的休闲游戏还是像小时候的像素游戏"比"你想要什么风格"有效十倍。答了的每一题，下一稿都要看得见。判断越准，问得越少。
5. **对用户不说术语。** 不说"响应式布局"，说"手机上不会乱"。
6. **惯例库公开、可贡献、带出处。** 作者不是专业游戏开发者，库要靠做过很多游戏的人一起长。每条都写清楚来源，没公开依据的如实标 `internal`。
7. **经验跟着用户走，不跟着项目走。** 项目日志只用来算指标；偏好、坑、案例放进用户自己的经验库，换项目、换工具都带得走。
8. **看图自检要留痕。** 看了什么、哪里不对，写下来才能交付。

## 路线图

- [x] v0.1 — H5 小游戏单一品类：规格协议 + 惯例库 + 静态验收器 + 样式补丁器
- [x] 真实浏览器验收（Playwright），一键安装，两张截图作为验收证据
- [x] v0.2 — 可执行的视觉标准 + 留存钩子清单 + 截图自检
- [x] v0.3 — 用户指出"标准定死了"：惯例库改为**选项库 + 判断指南**，协议改为**判断 → 提问 → 做 → 看图 → 再判断**，"太丑/不好玩"先诊断再回来问
- [x] v0.4 — 惯例库拆成四个文件、每条带出处、补一批公开来源的惯例、库校验器、贡献指南
- [x] v0.5 — 用户指出"经验要跨项目"：**经验库**（偏好 / 坑 / 案例，记在本机）；玩法库、受众库、出厂判断案例；按需读库；自检不留痕不能交付；提问次数等四个指标自动算
- [ ] v0.6 — 自动试玩出难度曲线；分享链接；接入用户自己的题目和图片；装到第二个 AI 工具；规则修改协议
- [ ] 之后 — 第二个品类（落地页 / 小工具）；把验收器、补丁器抽成可选的 MCP server

## Dogfood 日志

每次用 SayMake 从一句话做出一个东西，卡在哪里、改了什么，都记在 [`docs/dogfood-log.md`](docs/dogfood-log.md)。第一轮（接水果）的记录在那里。

## 非目标

- 不做通用提示词模板库
- 不做聊天壳、不做模型路由
- 不追求"一次就完美"，追求**可预期、可纠正、越用越准**

## 参与贡献

惯例库是公开的，欢迎往里加。作者不是专业游戏开发者——做过很多游戏、很多产品的人知道的"这种东西一般怎么做、为什么"，正是这个库最缺的。

- **加一条惯例**：新的视觉方向、玩法、机制、受众做法、判断案例、反模式。要带出处，具体到能照着做
- **补出处**：库里标 `internal` 的条目是摸索出来的，没有公开依据；知道它来自哪里就提 PR 补上。尤其欢迎有实战经验的人修正玩法库里的"怎么做"和默认数值
- **放一个例子**：在 `examples/` 里放一个你用 SayMake 做出来的小游戏，连同你当时说的那句话

格式、出处怎么写、提 PR 前跑什么，见 [`CONTRIBUTING.md`](CONTRIBUTING.md)。简单说：**每条惯例都要回答"它解决什么问题、什么时候它是错的、凭什么"。**
