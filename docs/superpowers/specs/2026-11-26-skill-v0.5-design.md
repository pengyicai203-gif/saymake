# make-game v0.5 设计：让判断有积累，让经验跟着用户走

日期：2026-11-26。依据：[`docs/skill-test.md`](../../skill-test.md) 的 14 条问题，以及用户在头脑风暴里的两条决定——先做"判断更准"并带上"记录"，以及**经验必须跨项目**。

## 目标

1. 模型每次判断时有案例可参照、有玩法可挑、知道给不同的人该改什么。
2. 每次对话自动留下记录，自检必须留痕。
3. 用户用得越久，skill 越懂这个用户：偏好、踩过的坑、判断案例跨项目累积，换项目、换工具都带得走。

不做：自动试玩和难度曲线、分享链接、接入用户自己的内容、第二个 AI 工具适配、规则修改协议。

## 一、两份案例

**出厂案例** `data/cases.json`：仓库自带，来自前五轮实测。每条是一段完整的中文叙述，不是表格：

```
用户的话 → 提到的信号 → 选的方向（审美 / 玩法 / 机制 / 字体）→ 为什么 → 问了什么、用户怎么答 → 结果（命中 / 偏了）→ 教训
```

**用户案例**：在用户自己的经验库里（见第四节），结构相同。协议里先看用户案例，再看出厂案例。

校验：案例引用的审美、机制、玩法 id 必须存在。

## 二、玩法库 `data/genres.json`

约 10 个被验证过的核心循环。每个玩法写：

| 字段 | 内容 |
|---|---|
| `oneLine` | 动词 + 失败条件 + 怎么计分 |
| `like` | 一句话"像什么游戏"，给用户挑的时候用 |
| `build` | 怎么做：页面元素还是画布、要不要物理、画布怎么放大不糊 |
| `defaults` | 默认数值：速度、间隔、大小、一局时长 |
| `dials` | 难度调哪几个旋钮，调了会怎样 |
| `mechanics` | 起步机制（引用 `mechanics.json`） |
| `audiences` | 适合谁 |
| `pitfalls` | 这个玩法最常见的做法错误 |
| `source` | 出处 |

用户只说"做个小游戏"时，从这里挑三个给他选，每个用 `like` 描述。

## 三、受众 `data/audiences.json`

给自己、给小孩、聚会轮流、给长辈。每条写清选了之后具体改什么：文字依赖、点按目标大小、失败怎么处理、节奏、字号、一局时长。问题库里加"想玩哪种"一问；"给谁玩"的答案从此影响决策。

## 四、按需读库 `scripts/library.mjs`

- `list`：只列清单，每个方向、玩法、机制一句话，目标 3KB 以内。
- `show <aesthetics|genres|mechanics|typography|audiences> <id>`：读一条完整的。
- `cases`：列出全部出厂案例的"用户的话"和教训。

协议改成：读 `conventions.json` + `list`，选中后 `show`。没有命令行的宿主退回直接读文件。

## 五、经验库 `scripts/log.mjs`

### 位置

- 项目日志：`<项目>/.saymake/session.jsonl`
- 经验库：`~/.saymake/memory/`（可用环境变量 `SAYMAKE_HOME` 改）。和 playwright 运行环境放一起，不在 skill 目录里——skill 升级时整个目录会被替换。

### 经验库三个文件

| 文件 | 一条长什么样 |
|---|---|
| `profile.json` | 偏好：`{ id, text, active, firstSeen, lastSeen, projects[] }`。同一句重复出现只更新时间；冲突时旧的置为 `active: false` |
| `cases.jsonl` | 用户案例：结构同出厂案例，多一个 `project` |
| `lessons.jsonl` | 坑：`{ id, time, project, problem, cause, fix, tags[] }` |

另有一个 `projects.jsonl` 记做过哪些项目，让模型知道"这个人做过什么"。

### 子命令

| 命令 | 写到哪 | 做什么 |
|---|---|---|
| `start --brief "…"` | 项目日志 + projects | 开工 |
| `judge --aesthetic … --genre … --mechanics … --audience … --why "…"` | 项目日志 + 用户案例 | 记判断 |
| `ask --question "…" --answer "…"` | 项目日志 + 用户案例 | 记提问 |
| `generate --file …` | 项目日志 | 写出了游戏文件 |
| `selfcheck --ok --notes "…"` | 项目日志 | 看截图后的自检，逐条写看到了什么 |
| `deliver` | 项目日志 | 交付。**上一次 `generate` 之后没有 `selfcheck` 就拒绝** |
| `feedback --kind overall\|local --text "…"` | 项目日志 + 用户案例 | 记反馈；`overall` 把案例结果记为"偏了" |
| `resolve --text "…"` | 用户案例 | 整体反馈解决后，写明最后是什么方向、教训是什么，案例结果改为"命中" |
| `remember --kind preference\|lesson --text "…"` | 经验库 | 记一条偏好或一个坑 |
| `forget <id>` / `show` | 经验库 | 删一条 / 给人看全部 |
| `recall --brief "…"` | 只读 | 给模型看：全部有效偏好、和这句话最像的最多 3 条案例、相关的最多 3 条坑、"这是第 N 个项目" |
| `summary` | 只读 | 四个指标 |

`recall` 的相似度用词面重合（不做向量），输出限制在 3KB 以内。

### 四个指标

| 指标 | 算法 |
|---|---|
| 提问次数 | `ask` 条数 |
| 首稿方向命中 | 第一次 `deliver` 之后的第一条 `feedback` 不是 `overall`；没有反馈则"未知" |
| 整体反馈次数 | `feedback overall` 条数 |
| 局部修改占比 | `local / (local + overall)` |

## 六、协议改动（`SKILL.md`）

- 第 0 步：`recall`，再 `list`，再读 `conventions.json`。
- 第 1 步：五个判断（审美、玩法、机制、字体、受众），先对照用户案例和出厂案例。没有玩法信号就问"想玩哪种"。
- 第 2 步：`judge`。
- 写出文件后：`generate`。
- 第 5 步：自检后 `selfcheck`，每条写看到了什么。
- 第 6 步：`deliver`。
- 第 7 步：`feedback`；整体反馈解决后 `resolve`；偏好和坑 `remember`。
- 结束时用一句话告诉用户记住了什么，并告诉他怎么看、怎么删。

## 七、顺手修

- `pixel-retro` 的 emoji 说法改为实测结论。
- `check_library.mjs` 扩展到新文件和跨库引用。

## 八、怎么验

1. `check_library.mjs` 通过。
2. `library.mjs list` 输出量 < 3KB；`show` 能读出完整条目。
3. `log.mjs` 用一轮假对话跑通：没有自检时 `deliver` 被拒；`recall` 能按相似度带出案例和偏好；`forget` 能删；`summary` 四个数对得上。
4. 只照着玩法库的条目做一款没做过的玩法（翻牌记忆），验收通过，看截图；记录条目哪里不够用。
5. 两个示例和两个模板重新验收。
6. 用户在新对话里说"帮我做个小游戏"，看是否触发、是否拿出玩法让他挑、是否先查了经验库。

## 九、已知局限

- 经验库只在本机。换电脑要手动拷 `~/.saymake/memory/`，暂不做同步。
- `recall` 是词面匹配，用户换了说法可能带不出来。
- 偏好要靠模型判断"这句话是不是长期偏好"，判断错时靠用户 `forget` 纠正。
- 没有命令行的宿主用不了脚本，只能直接读文件，经验库的自动记录也就没有了。
