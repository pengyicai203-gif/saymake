# Dogfood 日志

每次用 SayMake 从一句话做出一个东西，就在这里记一笔：用户原话、走了哪几步、哪里卡住、改了什么。卡点比成功更有价值。

---

## 2026-11-26 · 第一次：接水果

**用户原话：** "做一个在手机上玩的水果接取小游戏。"
**环境：** macOS，豆包工作，Node 22，skill 装在豆包用户 skill 目录 `.user_skills/make-game`
**结果：** 一轮生成通过验收（静态 9/9，浏览器 15/15），没有返工。产物：`examples/fruit-catch/index.html`

### 流程实际走法

| 步骤 | SKILL.md 要求 | 实际 | 顺畅？ |
|---|---|---|---|
| 0 读惯例库 | 填八成默认值 | 读了；"手机上玩"已是默认值，没问 | ✓ |
| 1 规格补全 | 最多两轮追问 → 复述 → 等确认 | **零追问**，"接水果"已经说清玩法；复述后直接继续 | ⚠ 见卡点 2 |
| 2 生成 | 以模板为骨架，满足契约 | 一次写成 | ✓ |
| 3 静态验收 | 必须全过 | 9/9 | ✓ |
| 3 浏览器验收 | `--browser` | 第一次跑就通，但截图是空的 | ⚠ 见卡点 4 |
| 4 交付 | 文件位置 + 三条标准 + 修改例句 | 见下 | ✓ |

### 卡点（按严重程度）

**1. 装进豆包后，当前会话看不到这个 skill。**
skill 列表在会话启动时加载，复制进去之后要新开对话才会被识别。这次是我手动按 SKILL.md 走的，等于绕过了"模型自己决定触发"这一步。
→ 协议本身没问题，但 README 的安装说明要写明"装完重开对话"。待办：新开对话验证 description 能否正确触发。

**2. 协议里没有"用户已经说开始做"的分支。**
SKILL.md 原来写的是"复述后让用户确认"，但用户这轮开头就说了"那你开始做吧"。严格照协议就该停下等确认，明显违背用户意愿。
→ 已改：复述完直接进第 2 步，复述是"不对随时打断"，不是关卡。

**3. 惯例库的 `alwaysAsk` 语义有歧义。**
`coreLoop` 标了 `alwaysAsk: true`，但"接水果"三个字已经是玩法了。实际没问，是对的；协议文字和实际行为不一致。
→ 已改：`alwaysAsk` 的含义改为"默认要问，用户原话已含玩法则不问"。

**4. playwright 装在哪里，之前没定义。**
两个坑：`npm init -y` 在 `~/.saymake` 目录下失败（包名不能以点开头）；如果装进 skill 目录，复制到宿主时会带上几百 MB 的 `node_modules`。
→ 已改：统一装到 `~/.saymake/`（约 600 MB，含 Chromium），新增 `scripts/setup_browser.sh` 一键安装；验收器按"仓库本地 → `~/.saymake`"两处查找，找不到就跳过并给出安装命令。

**5. 验收器截图时机太早。**
重启后立刻截图，水果还没生成，画面是空的，给用户看等于没看。另外计数把截图也算进了通过数，显示 "16/15"。
→ 已改：拍两张——开始页一张、运行 1.3 秒后一张；计数排除信息项。

**6. 验收器只能验证"能跑"，验证不了"好玩"。**
掉落速度、炸弹比例、接住判定的宽度舒不舒服，脚本测不出来。这次数值是我凭感觉定的，没有用户试玩反馈。
→ 这是产品层面的边界，不是 bug。下一步：用户试玩后说"太快了""篮子太小"，看补丁协议能不能精确落地。

**7. emoji 当素材的隐患。**
零依赖的做法是用 emoji 画水果和篮子，但 iOS、Android、Windows 上长得不一样。
→ 已写进惯例库：关键信息不能只靠 emoji 区分。

### 对协议的改动

- `SKILL.md`：规格补全加了"用户已授权直接做"例外；`alwaysAsk` 说明修正；验收步骤加 `setup_browser.sh` 和两张截图的交付要求。
- `conventions.json`：`coreLoop.note` 修正；新增 `defaults.assets`。
- `validate_game.mjs`：playwright 两处查找；两张截图；修计数。
- 新增 `scripts/setup_browser.sh`。

### 下一步要验证的

- 新开一个豆包对话，只说一句"做个接水果的游戏"，看 skill 会不会自动触发、会不会按协议走。
- 让一个不会代码的人试玩，收集前三条修改请求，看每一条能不能落到具体位置。
