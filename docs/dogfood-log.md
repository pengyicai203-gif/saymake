# Dogfood 日志

每次用 SayMake 从一句话做出一个东西，就在这里记一笔：用户原话、走了哪几步、哪里卡住、改了什么。卡点比成功更有价值。

---

## 2026-11-26 · 第一次：接水果

**用户原话：** "做一个在手机上玩的水果接取小游戏。"
**环境：** macOS，豆包工作，Node 22，skill 装在豆包用户 skill 目录 `.user_skills/make-game`
**结果：** 一轮生成通过验收（静态 9/9，浏览器 15/15），没有返工。产物：`examples/fruit-catch/index.html`

### 流程实际走法

| 步骤 | SKILL.md 要求 | 实际 | 顺畅？ |
|---|---|---|---|
| 0 读惯例库 | 填八成默认值 | 读了；"手机上玩"已是默认值，没问 | ✓ |
| 1 规格补全 | 最多两轮追问 → 复述 → 等确认 | **零追问**，"接水果"已经说清玩法；复述后直接继续 | ⚠ 见卡点 2 |
| 2 生成 | 以模板为骨架，满足契约 | 一次写成 | ✓ |
| 3 静态验收 | 必须全过 | 9/9 | ✓ |
| 3 浏览器验收 | `--browser` | 第一次跑就通，但截图是空的 | ⚠ 见卡点 4 |
| 4 交付 | 文件位置 + 三条标准 + 修改例句 | 见下 | ✓ |

### 卡点（按严重程度）

**1. 装进豆包后，当前会话看不到这个 skill。**
skill 列表在会话启动时加载，复制进去之后要新开对话才会被识别。这次是我手动按 SKILL.md 走的，等于绕过了"模型自己决定触发"这一步。
→ 协议本身没问题，但 README 的安装说明要写明"装完重开对话"。待办：新开对话验证 description 能否正确触发。

**2. 协议里没有"用户已经说开始做"的分支。**
SKILL.md 原来写的是"复述后让用户确认"，但用户这轮开头就说了"那你开始做吧"。严格照协议就该停下等确认，明显违背用户意愿。
→ 已改：复述完直接进第 2 步，复述是"不对随时打断"，不是关卡。

**3. 惯例库的 `alwaysAsk` 语义有歧义。**
`coreLoop` 标了 `alwaysAsk: true`，但"接水果"三个字已经是玩法了。实际没问，是对的；协议文字和实际行为不一致。
→ 已改：`alwaysAsk` 的含义改为"默认要问，用户原话已含玩法则不问"。

**4. playwright 装在哪里，之前没定义。**
两个坑：`npm init -y` 在 `~/.saymake` 目录下失败（包名不能以点开头）；如果装进 skill 目录，复制到宿主时会带上几百 MB 的 `node_modules`。
→ 已改：统一装到 `~/.saymake/`（约 600 MB，含 Chromium），新增 `scripts/setup_browser.sh` 一键安装；验收器按"仓库本地 → `~/.saymake`"两处查找，找不到就跳过并给出安装命令。

**5. 验收器截图时机太早。**
重启后立刻截图，水果还没生成，画面是空的，给用户看等于没看。另外计数把截图也算进了通过数，显示 "16/15"。
→ 已改：拍两张——开始页一张、运行 1.3 秒后一张；计数排除信息项。

**6. 验收器只能验证"能跑"，验证不了"好玩"。**
掉落速度、炸弹比例、接住判定的宽度舒不舒服，脚本测不出来。这次数值是我凭感觉定的，没有用户试玩反馈。
→ 这是产品层面的边界，不是 bug。下一步：用户试玩后说"太快了""篮子太小"，看补丁协议能不能精确落地。

**7. emoji 当素材的隐患。**
零依赖的做法是用 emoji 画水果和篮子，但 iOS、Android、Windows 上长得不一样。
→ 已写进惯例库：关键信息不能只靠 emoji 区分。

### 对协议的改动

- `SKILL.md`：规格补全加了"用户已授权直接做"例外；`alwaysAsk` 说明修正；验收步骤加 `setup_browser.sh` 和两张截图的交付要求。
- `conventions.json`：`coreLoop.note` 修正；新增 `defaults.assets`。
- `validate_game.mjs`：playwright 两处查找；两张截图；修计数。
- 新增 `scripts/setup_browser.sh`。

### 下一步要验证的

- 新开一个豆包对话，只说一句"做个接水果的游戏"，看 skill 会不会自动触发、会不会按协议走。
- 让一个不会代码的人试玩，收集前三条修改请求，看每一条能不能落到具体位置。

## 2026-11-26 · 第二轮：同一个游戏，用户试玩后的反馈

**用户原话（试玩 v1 之后）：**
> 1. 审美过时：游戏的背景、色彩，以及水果和篮子的形象等，都比较过时。就像是零几年互联网刚开始兴起、智能手机刚开始出现时的那种审美。
> 2. 吸引力不足：虽然有核心的游戏机制，但达不到现在对于游戏的要求，没有其他更多的吸引玩家的点，没有让玩家留下来一直玩的理由。

**这是最有价值的一类反馈**——用户不知道该提什么要求，但他一眼能看出"不对"。而 skill 的职责恰恰是替他补上他不知道的要求。

### 根因

两条都出在惯例库，不在生成环节：

| 反馈 | 惯例库里原来有什么 | 缺了什么 |
|---|---|---|
| 审美过时 | `visual` 一句"要有主题感、避免通用后台风格"；`assets` 写着"优先用 emoji" | 可执行的视觉标准（字体、字号、圆角、动效、禁止项）和配色预设。**"优先用 emoji"是直接肇事者** |
| 吸引力不足 | `loop`：开始→游玩→结束→重开；`difficulty`：三档递增 | 整个"留存"维度是空白。连击、稀有目标、阶段变化、历史最佳、打击感——一个字都没有 |

另一个根因在协议：**没有自检步骤。** 验收器只能验"能跑"，模型生成完看了眼"通过"就交付了，没有人（或模型）看过截图问一句"这好看吗"。

### 改动

**惯例库（`conventions.json` → v0.2.0）**
- `visual`：可执行标准——字体 `ui-rounded` 系、分数 ≥32px/800、卡片圆角 20–28px、动效 150–300ms 弹性缓动；**禁止 emoji 当主角**、硬阴影、斜面按钮、橙黄渐变、默认控件；三个配色预设（糖果明亮 / 夜市霓虹 / 薄荷清爽）带具体色值；主角画法配方"圆润主体 + 径向渐变 + 高光 + 装饰"。
- `retention`：7 个钩子清单（连击倍率、稀有奖励、阶段变化、历史最佳、打击感、险情提示、即时小目标），规则"默认至少 4 个，不问用户直接加"；结算页必须给"再来一局"的具体理由。
- `acceptance.model_self_check`：视觉 4 问 + 留存 2 问，由模型看截图回答。
- `defaults.storage` 改为默认记最佳成绩；`askUser` 新增 `mood`，选项直接用预设名。

**协议（`SKILL.md`）**
- 新增第 2 步"定视觉方向"：写代码前先定配色、主角画法、动效。
- 新增第 3.5 步"看截图自检"：验收通过后必须打开两张截图对照清单，不过就改，最多两轮。
- 修改请求新增 C 类"整体感受"（太丑 / 不好玩 / 像很老的游戏）：不问"你想要什么风格"，给预设名当选项；列缺失钩子直接加；给用户看改前改后。
- 铁律加一条：好看和好玩是默认要求，不是用户要提的需求。

**模板**：换成现代骨架——磨砂胶囊 HUD、居中卡片、胶囊按钮、弹性动效、CSS 变量配色。

**游戏（`examples/fruit-catch` v2）**：内联 SVG 画 5 种水果 + 炸弹 + 金苹果；连击 x1→x2→x3 带进度条；金苹果 ×5 更快；每 15 秒阶段变化（背景色 + 速度 + 炸弹率）；localStorage 历史最佳；粒子 + 飘字 + 篮子压缩回弹 + 震屏闪色；擦边漏掉飘"就差一点"；结算页给纪录、差距、一句评价。

### 这一轮新踩的坑

**8. "弹入"动效写在了屏幕外。** 第一版用 CSS transition 做出现动画，初始位置在 -999px，动画根本看不见。改用 Web Animations API 在真实位置弹入。→ 这是生成质量问题，自检截图时发现的（截图里水果一出现就是完整的，没有弹入过程）。暂时只能靠自检，脚本测不了动效。

**9. 自检发现主角偏小。** 第一版水果 44px、篮子 80px，截图看着空。放大到 54 / 96。→ 这类"看着不舒服但说不出哪不舒服"的判断，正是自检步骤存在的理由。可以考虑把"主角不小于屏宽 1/7"写进视觉标准。

### 结果

改前 / 改后截图见 `new-chat/验收截图/`。验收 15/15。

### 下一步要验证的

- 用户试玩 v2，看两条反馈是否消失。
- 在新对话里只说一句"做个接水果的游戏"，验证 skill 自动触发 + 新协议是否生效（这是真正要验证的东西，前两轮都是我手动走的）。
- 试一次 C 类修改：对 v2 说"太可爱了，想要酷一点的"，看它是否给预设选项而不是开放式提问。

## 2026-11-26 · 第三轮：用户指出 skill 的设计方向错了

**用户原话（要点）：**
> 惯例库里的惯例太少，审美标准太少。需要的不是死板地规定禁用什么，而是模型能判断：针对用户的任务，该用什么惯例、什么审美、什么机制、什么字体。判断不准就应该回来向用户提问。标准定死了，用户想要 10 年前的复古游戏，那就应该用 emoji。模型得判断"太丑""不好玩"是什么原因造成的，并回来问。做的过程中要主动提问，帮用户把模糊的想法梳理出完整性和画面感。

**这是对上一轮的直接否定，而且是对的。** 上一轮我把"v1 不好看"归因为"标准不够硬"，于是写了禁 emoji、字号不小于 32、默认至少 4 个钩子——把一个判断问题当成了规则问题。规则能防最坏的情况，但也防掉了最好的情况（用户要复古时，规则本身就是错的）。

### 根因

- 惯例库太薄：只有一种审美（现代休闲）、一个机制清单、没有字体方向、没有"什么时候不适用"。
- 协议把"少问"当成了目标。前两版都强调"最多两轮追问"，于是模型倾向于不问、自己猜、然后闷头做。
- 没有诊断步骤："太丑"只有"重做"一条路，没有"先找原因再问"。

### 改动

**惯例库 v0.3.0：从规则到选项库**
- `aesthetics.directions`：12 种视觉方向（现代休闲、像素复古、千禧年网页游戏、极简平面、手绘绘本、霓虹夜景、日系清新、美式漫画、剪纸层叠、拟物质感、蒸汽波故障、温暖秋日），每种带 feelsLike（用户能懂的一句话）、fits / avoid、配色、字体、形状、动效、素材画法、pitfalls。
- `mechanics.patterns`：14 种机制，每种带 fits / skip；`byGameType` 给起步组合；规则改为"去掉一个没差别就别加"。
- `typography.directions`：5 种系统字体方向。
- `decisionGuide`：信号→方向的映射和优先级（否定词 > 参考词 > 情绪词 > 题材词）；问题库（画面 / 参考物 / 受众 / 节奏 / 一局的意义 / 排除）；提问预算（每个检查点 ≤3 个，全程 3–6 个）；"太丑"6 条原因 + "不好玩"6 条原因，各带问法。
- 删除了所有 `forbidden` 式的审美硬规则，只保留契约和 16px 可读性底线。

**协议：判断 → 提问 → 做 → 看图 → 再判断**
- 第 1 步从"规格补全"改成"判断，并决定问什么"：先做审美/机制/字体三个判断并说得出依据，再看缺什么信号。
- 问题设计原则写进协议：用对比问、用参考物问、用排除法问、在检查点问、答了要看得见、不问技术。
- "太丑 / 不好玩"：先看截图按诊断清单找两三个原因，带着判断回来问，而不是重做。
- 新增"用户也说不清"的处理：排除法 + 参考物，一次一个。

**模板**：新增 `pixel-retro.html`，证明方向是选出来的。

### 这一轮的教训

**10. 用户反馈"结果不好"时，先分清是"标准不够"还是"判断不够"。** v1 的问题是我（模型）没看截图就交付了，是判断和自检的缺失；我却用加规则来修，结果矫枉过正。规则只能兜底，不能代替判断。

**11. "少问"不是目标，"问对"才是。** 之前把"最多两轮"当成铁律，其实是怕用户烦。但用户真正烦的是答了没用、和问他答不上的。帮他把画面变清楚的问题，他愿意答。

**12. 惯例库永远不够用，所以要允许合成。** 库的作用是给模型参照和一致性，不是穷举。协议里写明：没有合适的就自己合成一个方向，并告诉用户"我做的是 XX 感觉"。

### 下一步要验证的

- 用新协议在真实对话里跑：一句"做个接水果的游戏"，看它是否先判断、是否问出带画面的问题、用户答后是否看得见变化。
- 拿 v2 去试诊断流程：说"太可爱了"，看它是否带两三个原因回来问。
- 让用户提一个"复古"需求，验证库的宽度：比如"做一个像红白机那种的打砖块"。

## 第四轮：三个选项都不是——"更真实"

**输入**：针对第三轮给的方向选项，用户答："我想要的感觉都不在你的选项里。更真实：背景色彩更简单，水果和篮子更真实。玩完一局想要分数破纪录、放松解压、和朋友间比一比。"并提出两点新方向：公开惯例库让开发者贡献；抓取公开被验证过的惯例扩充。

### 发生了什么

- 我给的三个方向（糖果明亮 / 霓虹 / 像素 / 手绘）是从库里挑反差大的，但没有一个贴"真实"。库里当时根本没有"写实"这一档——这是库的缺口，不是选项设计的问题。
- 用户自己把感觉说清了：**"更真实 + 背景更简单"**。这是一条质感词信号，协议第三版里没有这一类信号，现在补上了（`fromUserWords` 的"质感词"）。
- "一局的意义"三个都要——所以机制是叠加的，不是单选。

### 改动

**游戏 v3（写实清爽）**
- 一色暖米背景，没有光斑、没有纹理。
- 水果重画：3 段以上径向渐变 + 模糊高光 + 表面细节（橙子柠檬的细孔、草莓的籽、葡萄的果粉）+ 果蒂叶子。篮子加编织 pattern 和内部阴影。
- 机制叠加：历史纪录（破纪录时有明显提示）+ 柔和反馈（解压）+ 两人轮流比一比 + 复制成绩。验收 15/15 通过。
- 自检：把所有主角放大到 130px 拍了一张 sprite sheet 看——草莓略像心形，整体可接受。

**惯例库 v0.4.0：拆分、带出处、能长**
- 一个 1000 多行的大 JSON 拆成四个文件：`conventions.json`（入口）+ `aesthetics.json` + `mechanics.json` + `typography.json`。
- 新增 4 种视觉方向：写实清爽（dogfood 来源）、卡通矢量、低多边形、赛璐璐。共 16 种。
- 从公开来源补了 8 条机制：一眼看懂、一句话说得清、一键重开、一局 45–90 秒、好看的失败、热身曲线、分层揭示、微目标；补 3 条反模式（功能倾倒、过早加运营系统、需要教程才懂）。共 21 条。
- 每条加 `source`：公开来源给 URL；自己摸索的标 `internal`；用户实测出来的标 `dogfood`。现在 45 条里 22 条是 `internal`——这是要靠社区补的。
- 新增 `scripts/check_library.mjs`：id 唯一、字段齐、跨库引用、出处格式。**第一次跑就抓出 16 处我自己写错的地方**（palette 没写成结构化的四项、一条 paper 来源没给 URL、字体引用写错）。库文件靠人手写，一定会写坏，校验器不是可选项。
- `CONTRIBUTING.md`：三类贡献、一条惯例怎么写、出处怎么写、"被验证过"的定义、提 PR 前跑什么。
- 协议：第 0 步改为读四个文件；第 2 步加"库没有就合成，认可后入库"；新增"答'都不像'用质感词追问一次"。

### 这一轮的教训

**13. 选项里的方向再反差大，也跳不出库的宽度。** 用户答"都不像"不一定是选项没设计好，可能是库里就没有那一档。所以"都不像"之后不要再列方向，要问质感词，然后把缺口补回库里。

**14. 用户说清感觉的那一刻，就是一条新惯例。** "更真实 + 背景更简单"直接变成了 `realistic-clean` 这一条。协议应该把这件事写成流程，而不是靠我每次想起来。

**15. 公开来源要读原文再写，不能只看摘要。** 这次补的 8 条机制来自 7 篇文章和一篇论文，每条都附了链接。有几篇是营销博客，观点有重复（一键重开、最佳分常显、险情提示被反复提到）——被反复提到的，可信度反而更高。

**16. 写库的人一定会写坏库。** 校验器第一次运行抓出 16 个错误。以后每个数据文件都配一个校验脚本，这是把"确定性交给脚本"用在项目自己身上。

### 指标基线（从这轮开始记）

| | 第一轮 | 第二轮 | 第三轮 | 第四轮 |
|---|---|---|---|---|
| 提问次数 | 1 | 0 | 0 | 1（方向选项） |
| 首稿方向命中 | 否 | 否 | 否 | **是** |
| 整体反馈次数 | 1 | 1 | 1 | 0 |
| 用户自己把感觉说清 | 否 | 否 | 部分 | **是** |

前两轮"整体反馈"是方向错；第三轮是协议错；第四轮用户说清之后一次命中。**结论：提问的价值在于帮用户说清，而不是替用户决定。**

### 下一步要验证的

- 新对话里说一句"做个接水果的游戏"，看 skill 是否自动触发、是否先判断再问。

## 第五轮：用头脑风暴过一遍，用户纠正了"经验放哪"

**起因**：用户要求先用"头脑风暴"的方式测一遍 skill，找出还缺什么。我先实测（复古打砖块、脚本盲玩接水果），再拿九种真实说法对着协议走查，列出 14 条问题，给了三个方向让用户选。

**用户选了**："判断更准"为主，带上"记录"里最小的两样。然后否决了我设计里的一条：

> 日志只存在项目自己的目录里，它就只是项目的日志。用户有好多个项目，其中一些问题、解决方案以及底层逻辑和经验是跨项目通用的。这个 skill 应该帮用户把经验和踩过的坑记录下来，存放在 AI 工具里面，用得越久越贴合用户。

**这是对的，而且我原来的设计把最重要的一块做小了。** 我把日志当成"算指标用的流水"，用户把它当成"这个 skill 替我攒下来的经验"。前者是给项目看的，后者是给模型看的——下一次开口的时候，它该知道对面是谁。

### 改动

**经验库**（`scripts/log.mjs`，数据在 `~/.saymake/memory/`）
- 偏好、做过的项目、踩过的坑、判断案例，四样。不在 skill 目录里——那里升级会被整个替换。
- 开工 `recall`：按相似度带出偏好、最多 3 条相似案例（带结果和教训）、最多 3 条相关的坑。
- 做完 `remember`：偏好、坑。用户说"忘掉"就 `forget`。纯文本，不上传。
- 交付关卡：`generate` 之后没有 `selfcheck` 就 `deliver`，拒绝。

**让判断更准**
- 玩法库 11 个：一句话、像什么、怎么做、默认数值、难度旋钮、适合谁、常见错误。用户只说"做个小游戏"时，从这里挑三个给他选。
- 受众 4 种：给小孩、聚会、给长辈，各自具体改什么。点按目标大小有公开出处。
- 出厂判断案例 5 条：四轮接水果加一次打砖块，偏了的和命中的都写清为什么。
- 按需读库：先读 1500 字的清单，选中哪条读哪条。
- 协议改成七个判断点和一条收尾：开工查经验 → 判断 → 记判断 → 生成 → 验收 → 看图留痕 → 交付 → 记住这一轮学到的。

### 这一轮的教训

**17. "记录"有两种，别做成一种。** 项目日志回答"这次做得怎么样"，经验库回答"这个人是谁"。前者跟着项目走，后者跟着人走。混在一起，换项目就丢。

**18. 库里的一句话，模型可能理解反。** "填色不满边"我做成了往外偏。条目要写到"照着做不会做反"的程度，最好带做法。每条惯例被实测过一次之前，都当它是草稿。

**19. 脚本能拦住的和拦不住的要分清。** 没自检不能交付，脚本拦得住；看了不记、直接改，脚本拦不住，我自己就犯了。能变成脚本的别靠自觉，不能的就如实写进局限。

**20. 测试的人和写的人是同一个，是一种偏乐观。** 我知道库里有什么，所以走查时不会"想不到"。真实用户第一次用，卡的地方多半不在我的清单里。所以新对话里的那次验证不能省。
