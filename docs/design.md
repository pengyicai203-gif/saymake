# 设计说明

这份文档解释 SayMake 为什么长这样。写给想改它的人。

## 问题

大模型很强，但普通人用不好它。原因不是模型不够强，而是**信息通道太窄**：用户脑子里有一张完整的图，能说出来的不到十分之一。

现在的产品大多在帮用户"说得更准"（提示词模板、技巧），但没解决两件更根本的事：

1. 用户**说不清**自己要什么——这是"想清楚"的问题，不是"会说话"的问题
2. 用户**看不懂**结果对不对——验收依赖专业知识和术语

提示词工程之所以难，是因为它要求人同时做这两件事。SayMake 把这两件事从用户侧搬到系统侧。

## 一句话定义

> 用户只负责说清楚想要什么，系统负责把它翻译成可执行的规格、生成看得见的东西、自动验收，并在用户说"不对"时知道该改哪里。

## 四个部件

### 1. 规格补全协议（`SKILL.md`）

一句模糊的话进来，系统先把它变成用户确认过的规格。关键设计：

- **最多两轮追问。** 超过两轮用户就烦了。每个问题给选项，不出开放题——人辨认想要的比描述想要的容易得多。
- **复述 + 三条验收标准。** 把不可测的"满意"换成可测的"这三条过了吗"。
- **不说术语。** 验收标准必须是用户肉眼能判断的事："打开就能玩""点一下分数会变""手机上不会乱"。

### 2. 惯例库（`data/*.json`）

一个品类里八成以上的决策是行业惯例，根本不该问用户：竖屏、单局时长、点按操作、无外部依赖、默认不加音效。这些写成数据而不是写进提示词，原因有三：能被版本管理、能被测试、能让社区贡献。

v0.3 的教训：**惯例不能写成规则。** 写成"禁用 emoji""字号不小于 32"，用户要一款十年前的复古游戏时就全错了。所以库里现在只有两类东西：

- **选项**：16 种视觉方向、21 种机制、5 种字体方向。每条都写了"适合 / 不适合"和"具体怎么做"（配色给色值、时长给秒数、主角怎么画）。
- **判断指南**：从用户的话里提哪些信号、信号冲突时谁优先、拿不准时问什么、用户说"太丑 / 不好玩"时怎么诊断。

库是四个文件：`conventions.json` 是入口（默认值、判断指南、验收、契约），`aesthetics.json` / `mechanics.json` / `typography.json` 是三个库本体。每条带 `source`，没公开依据的如实标 `internal`。`scripts/check_library.mjs` 保证库不会长坏。库没有合适方向时，协议允许模型合成一个，用户认可后加回库里——**库的每一个缺口都应该变成一条新条目。**

### 3. 验收器（`scripts/validate_game.mjs`）

这是整个项目的命根子。原则：**用"过不过"替代"像不像"。**

静态检查无依赖，秒级完成：单文件、viewport、契约标记、脚本语法、API、禁止弹窗、体积。

`--browser` 模式用真实浏览器：加载无报错、手机宽度无溢出、`start()` 后进入运行态、`getScore()` 返回数字、点击不报错、`restart()` 能重开，并留一张截图给用户看。

验收器的输出是给**模型**看的——它据此修。用户看到的只是"三条标准都过了"。

### 4. 补丁器（`scripts/patch_css.mjs`）

"这块大一点"必须落到具体元素的属性上，而不是重写整个文件。覆盖样式统一写在 `<style id="sm-overrides">`，同一选择器替换而不叠加，可列出、可清除。玩法逻辑的修改则直接编辑逻辑区的相关行。

## 契约

生成器和验收器之间有一份显式契约（`conventions.json` → `contract`）：

```
data-sm="start" | "score" | "restart"
window.__sm = { start, restart, getScore, isRunning }
```

这是整个设计里最不起眼但最关键的部分。没有契约，验收只能靠模型"看一眼觉得没问题"；有了契约，验收是确定性的，修改可以精确定位，回归测试成为可能。

将来扩到第二个品类，第一件事就是定义那个品类的契约。

## 提问的成本与引擎的准确率

提问不是越多越好，也不是越少越好。用户一开始只有一个模糊的画面，**帮他梳理画面本身就是产品价值**；但每多问一句，门槛就高一分。两头要同时优化：

- **降低每个问题的成本**：选项永远是画面不是术语；能多选就多选；先给一稿再问（对着实物说"不对"比对着空气描述容易）；用户答"都不像"时用质感词追问一次，不重新列方向。
- **提高判断的准确率，让需要问的问题变少**：判断越准，首稿就越接近用户心里的东西，剩下的只是微调。

要能量化，否则"越用越准"是空话。从 v0.5 起每轮 dogfood 记四个数：

| 指标 | 含义 | 怎么算 |
|---|---|---|
| 提问次数 | 用户总共答了几个问题 | 数 |
| 首稿方向命中率 | 第一稿的整体方向用户是否认可（不需要"换方向"级别的修改） | 是 / 否 |
| 整体反馈次数 | 用户说"太丑 / 不好玩 / 不像"这类整体感受反馈的次数 | 数 |
| 局部修改占比 | 修改请求里"指哪改哪"类占比 | 局部数 / 总修改数 |

目标是：提问次数不升，首稿命中率上升，整体反馈次数下降。前四轮的基线在 dogfood 日志里——两轮"整体反馈"都是因为方向错了，而且都是我给的选项里没有用户要的东西。

## 公开惯例库的策略

库是这个项目最值钱也最脆弱的部分：作者不专业，一个人写不出"被验证过的惯例"。所以：

1. **每条带出处。** 公开来源（文章 / 论文 / 书）给 URL；自己摸索的标 `internal`；用户实测认可的标 `dogfood`。不伪装成有出处。
2. **只收"被验证过"的。** 有公开来源，或经过真实用户测试并明确认可，二者至少占一个。
3. **每条都要写"什么时候是错的"。** 没有反例的惯例通常是死规则，会被拒。
4. **机器校验。** `check_library.mjs` 管 id 唯一、字段齐全、跨库引用、出处格式。审美层面由 PR 评审把关。
5. **缺口驱动。** 协议遇到库没有的方向，先合成、再验证、再入库。库是被真实使用逼着长出来的，不是一次设计完的。

抓取公开来源的原则：读原文，按它的意思写条目并附链接；不整段搬运，不编造出处，不把没读过的文章写进 `source`。

## 原则

1. **判断交给模型，确定性交给脚本。** 模型负责理解、追问、生成；脚本负责验证、修补。绝不相信模型口头说"能跑"。
2. **用"过不过"替代"像不像"。** 每条验收标准都必须可执行、可回归。
3. **用"选"替代"说"。** 候选之间要有真实差异。
4. **八成的决策不该问用户。** 问得越多，体验越差，答案越不准。
5. **对用户不说术语。** 这是最后一公里，缺了前面全白做。

## 边界

- 不做聊天壳。用户已经在用豆包、Codex、Claude Code，SayMake 装进去就好。
- 不做模型路由。那是宿主的事，而且会迅速商品化。
- 不做提示词模板库。仓库里代码和数据的占比必须高于提示词，否则没有壁垒。
- 不承诺"一次完美"。承诺的是**可预期、可纠正、越用越准**。

## 已知局限

- 验收器只能验证"能用"，验证不了"好玩"。玩法的好坏仍然依赖生成质量和用户反馈闭环。
- 样式补丁走 CSS 覆盖，适合大多数视觉调整；结构性改动（加一个面板、换布局）仍需模型直接编辑文件，精度取决于模型。
- 偏好记忆目前是一个 Markdown 文件，跨项目、跨设备的同步还没做。
- skill 在新对话里能否自动触发、并真的按协议主动提问，还没有在真实对话里验证过——前四轮都是作者手动按协议走的。v0.5 第一件事就是验这个。
- 惯例库 45 条里，标 `internal` 的有 22 条没有公开出处；它们是从实测里来的，但没经过更大样本的验证。

## 路线

- v0.1：单品类打穿闭环。目标是自己用、朋友用，把卡点记下来。
- v0.2：浏览器验收默认开启；视觉标准与留存钩子。
- v0.3：用户指出"标准定死了"——惯例库改为选项库 + 判断指南，协议改为判断 → 提问 → 做 → 看图 → 再判断。
- v0.4：惯例库拆分、每条带出处、补公开来源、库校验器、贡献指南——让库能靠社区长。
- v0.5：在真实对话里跑新协议，记录提问次数 / 首稿命中率；逻辑补丁协议；偏好记忆结构化。
- 之后：第二个品类（落地页或小工具），验证"惯例库 + 契约 + 验收器"这套结构能不能复用；把验收器、补丁器抽成可选的 MCP server，适配没有 bash 能力的宿主；打包成各家插件。
