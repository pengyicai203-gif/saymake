# make-game skill 测试记录（2026-11-26）

目的：对着最初的想法——"不懂代码的人用一句自然语言做出想要的东西，skill 负责判断、必要时提问、做出来、能验收、能指哪改哪"——找出 skill 还缺什么。

先说测试的局限：**写 skill 的人和测 skill 的人是我同一个。** 我知道库里的每一条，所以"模型会怎么判断"这部分测不准；而且 skill 在新对话里会不会自动触发，在这个对话里验不了。下面把"实测"和"走查"分开标。

## 一、实测（跑了的）

| 测试 | 做法 | 结果 |
|---|---|---|
| 脚本可用性 | 从豆包的安装目录（路径带空格）、在别的目录下运行校验器和验收器 | 通过 |
| 库校验 | `check_library.mjs` | 通过，45 条 |
| 真做一款：复古方向 | 按协议做"像红白机那种的打砖块" | 验收 15/15；截图对照"像素复古"的感觉，一处不像（见问题 1） |
| 验收器能不能判断"好不好玩" | 让脚本闭着眼左右扫 15 秒玩接水果 v3 | 能跑，但只能得到"分数 0→1→0"。不知道难不难、好不好玩 |
| 自动触发、主动提问 | — | **没测**。需要在新对话里做，见文末 |

## 二、走查（拿真实说法对着协议过了一遍，没真做）

| 用户可能这么说 | 卡在哪 |
|---|---|
| "帮我做个小游戏" | 库里没有"可以做什么游戏"。问题库里问了画面、受众、节奏、意义，**唯独没有问玩法**。协议只能默认做接水果那类 |
| "做个给小孩玩的认颜色游戏" | 问题库有"给小孩玩"这个选项，但选了之后库里**没有任何一条**说给小孩该怎么做（要不要文字、要不要失败、点多大）。也没有教育/答题这个玩法类型 |
| "做个合成大西瓜那种" | 库里提到"合成类"，但没有怎么做。默认值写"优先 DOM"，这类游戏其实该用低分辨率画布 + 简单物理，这条知识不在库里，靠模型自己会 |
| "答题小游戏，题目是我准备的 20 道题" | 协议没有"用户拿出自己的内容（文字、表格、图片）怎么接进来"这一步 |
| 玩完说"太简单了" | 诊断清单写着"看一局数据：分数分布、存活时间"——**没有工具能拿到这些数据**。也没有"这个玩法默认掉多快、隔几秒出一个"的参考数值 |
| "让炸弹少一点，篮子大一点" | 前半句是规则修改，没有像样式补丁那样的协议，靠模型直接改代码 |
| "发个链接给朋友" | 只能给一个文件。没有分享/部署路径，也没说手机上怎么打开 |
| "做个生日祝福页面发朋友" | 不是游戏。skill 没写"超出范围时怎么办" |

## 三、问题清单

按"离最初的想法有多远"排，越靠前越关键。

1. **库里的建议会错，而且错了没人发现。** 像素复古方向写着"可以用 emoji"。实测里 emoji 爱心是光亮的立体心，放在平面像素里一眼跳出来，最后是我手画了一颗像素心才对。库只管"有没有这一条"，不管"这一条照着做出来对不对"。
2. **"判断"全凭模型当场想，没有案例。** 四轮实测里，用户的话 → 选了什么方向 → 为什么，这些判断没有一条沉淀进库。新对话里的模型是从零开始判断的，会重复我犯过的错（第一轮没看截图就交付、第二轮把判断问题当规则问题）。
3. **"好不好玩"没有任何测量手段。** 验收器 15 项验的全是"能跑"。游戏太简单、太难、节奏太平，只能靠人玩。契约只暴露了开始/重开/分数/运行状态，脚本没法可靠地替人玩。
4. **"越用越准"没有数据来源。** 提问次数、首稿命中率这些指标写在设计文档里，但 skill 不记录每次的信号、判断、问了什么、用户怎么答。指标靠人手填，填几轮就会停。
5. **自检可以悄悄跳过。** 协议要求"看截图对照方向自检"，但不要求留下任何痕迹。跳过了也没人知道——第一轮我就是这么错的。
6. **只有"长什么样"的库，没有"怎么做"的库。** 16 种审美方向、21 条机制都是设计层；具体到"打砖块怎么搭、合成类怎么处理碰撞、低分辨率画布怎么放大才不糊"，库里没有。
7. **没有玩法起步库。** 用户只有一个模糊念头时，拿不出"这几个玩法已经被验证过、一句话能说清"的清单给他挑。
8. **受众是空话。** 问了"给谁玩"，但答案不影响任何决策。
9. **每次对话要读约 5 万字符。** SKILL.md 加四个数据文件全读。方向其实只用得上一个。
10. **用户自己的内容进不来。** 题目、图片、商品信息、文案，都没有接入步骤。
11. **只能给文件，给不了链接。**
12. **范围外没有说法。** 不是游戏的需求，skill 没说该拒绝、改做还是推荐别的。
13. **只装过豆包。** 用户想用的是 Codex、WorkBuddy 这些，没试过。
14. **22/45 条惯例没有公开出处。**

## 四、对应最初的想法

| 最初的想法 | 现在 | 缺口 |
|---|---|---|
| 判断该用什么惯例、审美、机制、字体 | 有判断指南和选项库 | 没有判断案例；库条目可能错（1、2） |
| 判断不准就回来问，帮用户把想法梳理清楚 | 有问题库和提问预算 | 不问玩法；受众答案没用（7、8） |
| 做出来 | 能做，两个方向验证过 | 缺"怎么做"的库（6） |
| 可视化，让用户直接确认 | 有截图 | 截图看不出手感（3） |
| 自然语言指哪改哪 | 样式有补丁器 | 规则修改没有协议（走查第 6 行） |
| 越用越准、提问越来越少 | 有指标定义 | 没有记录，指标算不出来（4、5） |
| 公开惯例库、大家来补 | 有贡献指南和校验器 | 校验只验格式，不验内容对不对（1） |
| 拿到一个能直接用的链接或文件 | 文件 | 链接、用户素材、其他 AI 工具（10、11、13） |

## 五、下一次要验、但我验不了的

新开一个对话，直接说：

> 帮我做个小游戏

看三件事：skill 有没有自动触发；它是不是先拿出几个玩法让你挑（现在做不到，这是已知缺口）；它问的问题是不是带画面的选项。
